## GC-6 — opening width is the projection onto the matched wall

**Status: DONE.**

### What changed

`src/pwa/floorplan/normalize.py`:

- Added `_projected_opening_width_m(span, wall)` — projects both span endpoints onto the matched
  wall's unit direction vector (the same "t" parameter already used by `_resolve_wall_id`) and
  returns the quantized absolute difference. This is the wall-parallel extent of the opening,
  independent of any perpendicular offset in the raw span.
- In `normalize()`, the opening-processing loop was reordered: `width_m` is now computed **after**
  `wall_id` resolution, not before. When the opening carries a raw span (DXF only — annotation
  openings never have `span`) **and** wall resolution succeeded (`wall_id != _PENDING_DXF_WALL_ID`),
  `width_m` comes from `_projected_opening_width_m`. Otherwise (annotation openings, or a DXF
  opening whose wall resolution is still pending) it keeps the previous behavior: the declared/raw
  `opening.width_m`, quantized. `validate()`'s independent re-check of unresolved DXF openings is
  unaffected.
- Added a new invariant: if the projected width quantizes to `<= 0` (a span collinear enough to
  resolve to a wall but with zero along-wall extent — e.g. a line drawn perpendicular to, and
  centred on, the wall), `normalize()` raises the **existing** `PARSE_RESOURCE_LIMIT` finding with
  the same message already used a few lines above for a non-finite/non-positive declared width.
  No new error code was introduced — `contracts/error_codes.md` was not touched.
- `dxf_worker.py` was deliberately left unchanged: its raw `hypot()`-based `width_m` remains an
  input value (used for the initial finite/positive sanity check and as the fallback when there is
  no span or wall resolution hasn't succeeded), but it is no longer what ends up in
  `NormOpening.width_m` for a resolved DXF opening — that is now always the projected value.

## GC-7 — strip source metadata from the raster overlay

**Status: DONE.**

### What changed

`src/pwa/floorplan/builder.py`:

- Added `_sanitize_raster_bytes(image, media_type)`: re-encodes the already-decoded `PIL.Image`
  through Pillow with pinned encoder settings (`_SANITIZED_JPEG_QUALITY = 95`,
  `_SANITIZED_PNG_COMPRESS_LEVEL = 6`), never forwarding `exif=`, `pnginfo=`, or `icc_profile=`.
  Pillow does not carry `image.info`/EXIF back out of `save()` unless a caller explicitly passes it
  back in, so this strips EXIF, PNG `tEXt`/`iTXt` chunks, ICC profiles, and DPI metadata by
  construction — verified directly (see tests below).
- `_source_binding()` now calls `_sanitize_raster_bytes()` instead of `source_path.read_bytes()`
  for the `image_bytes` field that `overlay.py` base64-embeds. No dependency was added — Pillow was
  already a project dependency and is the only library used.
- `source_sha256` in the returned binding is **unchanged**: it was already `sha256_file(source_path)`
  (reads the original file from disk), and still is. This is the hash bound into the overlay's
  `<metadata>` block by `overlay.py::_metadata()`. It was not touched, and is explicitly proven
  below to still equal the original bytes' hash, not the sanitized copy's.
- Media-type derivation from decoded format (PNG-vs-JPEG, M-5 fix from the prior review round) is
  unchanged and still correct.

### Deliberately out of scope

The literal requirement — "keep MAX_SOURCE_RASTER_BYTES / MAX_SOURCE_PIXELS / MAX_OVERLAY_BYTES
caps effective; sanitizing must not bypass a size check" — is satisfied: all three caps are still
checked (in `overlay.py::_raster_svg`) against the values that actually end up embedded
(`image_bytes` is now the sanitized bytes, and `width_px`/`height_px` are unchanged, cheap
header-only reads), so none of the three caps can be silently bypassed by a source that is
oversized post-sanitization. I did **not** additionally restructure control flow to reject an
oversized raw file *before* the Pillow decode required to sanitize it (i.e., there is no new
pre-decode short-circuit). Two reasons: (1) PLAN §10 itself requires embedding "decoded pixel
data," which inherently requires a full decode — this is the same disclosed residual resource risk
already recorded in PLAN §12 ("Part 1 has no portable hard RSS/memory limit on Windows... any
hard-memory sandbox is deferred rather than falsely claimed"), not a new one; (2) `_source_binding()`
is called outside the specific `try/except ValueError` block in `builder.py::parse_run()` that
maps `render_overlay()`'s size-limit exceptions to `PARSE_RESOURCE_LIMIT` + CLI 3 — raising a new
exception type from inside `_source_binding()` would need to reuse that exact exception contract or
risk falling through to the generic operational-failure path (CLI 2, wrong outcome per the §11
decision table), which is more than a two-clause GC-7 change should touch without a human decision.
Flagging this explicitly rather than silently expanding scope, per the escalation instruction.
