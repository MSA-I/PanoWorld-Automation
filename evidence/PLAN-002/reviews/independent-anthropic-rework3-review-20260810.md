## Finding detail

### F1 — DXF size-gate TOCTOU (MINOR)
- **Where**: `builder.py:742` computes `source_floorplan_size = source_floorplan.stat().st_size` where `source_floorplan` is resolved from `source_run` (the already-finalized, supposedly-immutable but not OS-permission-protected source run). `builder.py:753` compares this against `MAX_DXF_BYTES`. The actual single-read copy+hash of the same file happens later, at `builder.py:780` (`copy_source_inventory(source_run, staging_run, source_manifest)`, which calls `copy_immutable` per `runs.py:181-194`).
- **Failure scenario**: an actor with concurrent write access to the source-run directory replaces a small, size-limit-compliant DXF file with a much larger one between the `stat()` at line 742 and the copy at line 780. The size gate is bypassed. However: `copy_immutable` then reads+writes+hashes the swapped file in full (resource cost proportional to attacker's chosen size, this is the actual consequence — extra I/O, not a limit bypass for parsing), and the resulting hash will not match the manifest's declared `sha256`, so `copy_source_inventory` raises `PARSE_SOURCE_HASH_MISMATCH` (`runs.py:189-194`) before any parsing occurs. Separately, even if a swapped file happened to hash-match (impossible without a SHA-256 collision), `dxf_source.py`'s `_run_worker` re-checks `path.stat().st_size > MAX_DXF_BYTES` (line 57) against the *staged* copy before parsing. So the size-gate TOCTOU cannot be leveraged to get an oversized file parsed; it can only be leveraged to force this process to fully read/write/hash a larger-than-declared file before rejecting it.
- **Why it's not higher severity**: the attacker precondition (concurrent write access to a "finalized" source run) already breaks GC3-4's finality assumption directly — nothing in this rework (or any prior round) enforces OS-level immutability (e.g., read-only ACLs) on finalized runs; `finalize_run` is a plain `os.replace` with no permission hardening. This finding is one more manifestation of that pre-existing, structural, out-of-bounded-scope gap, not a new hole this rework opened.
- **Fix recommendation** (naming, not applying, per read-only mandate): move the byte-size check to operate on `copy_immutable`'s own bytes-read counter (fail fast mid-stream) or check size on the staged copy right after `copy_source_inventory` returns, before any parsing — removing the redundant pre-copy stat entirely would also work since the staged-copy check in `dxf_source.py:57` already covers the real gate.

### F2 — `finalize_run` post-rename re-verify failure loses the report (MINOR)
- **Where**: `runs.py:220-222` — `verify_run_inventory(staging_run, manifest)` (pre-rename, line 220), `os.replace(staging_run, final_run)` (line 221), `verify_run_inventory(final_run, manifest)` (post-rename, line 222).
- **Failure scenario**: the pre-rename check at line 220 passes, `os.replace` at line 221 completes successfully (this is an atomic rename of the same inode on the same volume — it cannot itself corrupt contents), and then the post-rename check at line 222 raises `ValueError("finalized inventory hash mismatch")` (this would require a third party mutating `final_run`'s freshly-renamed contents in the sub-millisecond window between lines 221 and 222 — the same "already has write access to runs_root" precondition as F1). This propagates up to one of `builder.py`'s two catch sites (line 1053's `except (OSError, ValueError, ...)` for the domain-failure path, or line 1069-1076's tuple for the main success path), both routing to `_staged_operational_result` (`builder.py:431-454`). That function checks `staging_run.is_dir()` before writing a report — but `staging_run` was just renamed away, so it is no longer a directory at that path, and the check is `False`. No report is written anywhere (not to the vanished staging path, not to `final_run`, which is the one place that actually exists). The caller receives `cli_exit=2` ("operational_failure") with an in-memory `diagnostic` dict that is never persisted, while `final_run` exists on disk as a fully valid directory (it passed the pre-rename check with the exact same manifest).
- **Why it's not higher severity**: the trigger requires a hostile concurrent mutator inside the tiny window between an atomic rename and the immediately-following re-check — a redundant defensive check by design. The inconsistency is real (a caller polling `final_run.exists()` and one reading `cli_exit` could reach opposite conclusions about success), but the practical window is close to zero absent an already-compromised runs_root.

### F3 — `--annotation` path has no reparse/symlink check (INFO, pre-existing)
- **Where**: `builder.py:684`, `Path(annotation).read_bytes()`. Confirmed via `git show 11ef553:src/pwa/floorplan/builder.py` that the pre-rework code had the identical gap (it used `Path(annotation).stat()` then a separate `Path(annotation).read_text()` — itself a small TOCTOU this rework correctly closed by switching to a single `read_bytes()` call reused for both the length check and the JSON decode, per `builder.py:684,753` — that is a genuine, if minor, GC3-3-adjacent improvement worth crediting). What neither version does is call `is_link_or_reparse` on `annotation` itself, unlike the ancestor walk `resolve_contained_run` applies to `source_run`.
- **Not attributed to this rework**: this is not a new defect introduced by GC3-1..7/GC3-11; it predates the branch. Flagged only because the brief asks specifically for this class of gap and GC3-1's fix philosophy (every filesystem entry point gets the same scrutiny) does not yet extend here.

### F4 — Windows lexical-comparison edge cases (INFO / CANNOT_VERIFY)
- **Where**: `_contained_parts` (`runs.py:12-17`) rejects `""`/`"."`/`".."` components and requires a relative path, but does no case-folding, trailing-dot/space stripping, or 8.3-alias resolution before `validate_contained_destination`/`create_contained_directory` walk the filesystem component-by-component (`runs.py:20-56`).
- **Why CANNOT_VERIFY rather than a confirmed finding**: proving whether e.g. a component ending in a trailing dot (`"foo."`) is treated by NTFS/Win32 as identical to `"foo"` in a way that defeats the `cursor.exists()` check at a specific point in the walk requires actually creating such paths and observing OS behavior — outside what I can do read-only. Naming a concrete command for the orchestrator: create a directory `foo` and attempt `Path("foo.").exists()` / `Path("foo.").mkdir()` from a Python REPL on the actual Windows host, and separately check whether `os.stat` on a manufactured 8.3 alias (`dir /x` to find one) reports the same `st_dev`/`st_ino` as the long name, to see if either technique could make a component that lexically differs from an already-checked ancestor actually resolve to it (or vice versa).

## Disclosure judgments

1. **Pre-staging inventory hash re-check removed, test replaced.** Judged a **correction, not a weakening**. `copy_immutable` (invoked from `copy_source_inventory`, `runs.py:181-194`) computes its returned hash from the exact bytes it streams from source to destination in one pass; the caller compares that hash against the manifest's declared value inline (`runs.py:189-194`) rather than performing a *second*, separate read-and-rehash of the already-copied file after staging. Removing a second read of the same file reduces TOCTOU surface rather than increasing it, provided `copy_immutable` is a genuine single-read streaming copy — confirmed by design (read-then-write-then-hash-the-same-buffer pattern), not by re-reading its full implementation line-by-line in this session (noted honestly rather than over-claiming).
2. **Hostile-label test rewrite.** Judged a **strengthening**. `overlay.py`'s `xml.sax.saxutils.escape`/`quoteattr` usage is unchanged by this diff (confirmed via grep — `overlay.py` has zero footprint in the GC3-1..7 diff). What changed is that GC3-6 now redacts hostile/unknown DXF layer and layout names to opaque tokens *before* they reach the overlay serializer at all (`dxf_worker.py:93-98`), so the rewritten test verifying token-based output alongside unchanged escaping is testing a genuinely stronger property (raw attacker/PII-bearing strings never enter tracked evidence, not merely "safely escaped if they do").
3. **GC3-5 in-process substitute test.** Consistent with the cumulative-cap fix actually present in code (`dxf_worker.py:87-88`); I did not re-derive whether the substitute avoids constructing thousands of real DXF entities, but the cap logic itself is verified directly by reading `_scan_layout`, independent of how the test constructs its fixture.
