# מתודיקת ניהול, פיקוח ותיעוד לסוכני AI

## המטרה
לאפשר פרויקט של עשרות סבבים בלי לאבד הקשר, בלי לבצע עבודה כפולה ובלי לקבל טענות “הושלם” שאינן מגובות בראיות.

## עיקרון על
הצ'אט אינו מקור האמת. מקור האמת הוא שילוב של:
1. Git.
2. `PROJECT-STATE.yaml`.
3. תוכנית הגל הפעיל.
4. artifacts ו-evidence.
5. דוחות test/run.
6. decision log.
7. `08-מדיניות-ניהול-מודלים-וסוכנים-deepseek-first.md` עבור ניהול ו־fallback; מסמך 06 מגדיר את הניתוב לפי תפקיד.
8. מסמכים 09–10 עבור gates ותת־הגרף של כל WP.

## שפת סטטוסים אחידה
מותר להשתמש רק בסטטוסים הבאים:

- `NOT_STARTED` — טרם תוכנן לביצוע.
- `PLANNED` — קיימת תוכנית מאושרת.
- `READY` — כל התלויות עברו.
- `IN_PROGRESS` — סוכן עובד ומוגדרת בעלות.
- `BLOCKED` — חסם מפורש עם owner ו-next action.
- `REVIEW` — הוגש לבדיקה, עדיין לא מאושר.
- `REWORK` — review נכשל ונדרש תיקון.
- `VERIFIED` — עבר gates עם evidence.
- `MERGED` — מוזג לענף הראשי.
- `DONE` — מוזג, docs עודכנו ואין blocker פתוח.
- `CANCELLED` — בוטל בהחלטה מתועדת.

אסור להשתמש במילים עמומות כגון “כמעט מוכן”, “נראה תקין” או “אמור לעבוד” כסטטוס.

## מזהים
- תוכנית: `PLAN-###-short-name`.
- סבב: `ITER-YYYYMMDD-###`.
- ריצה: `RUN-YYYYMMDD-HHMMSS-<short-hash>`.
- החלטה: `ADR-####`.
- חסם: `BLOCK-####`.
- handoff: `HANDOFF-<producer>-to-<consumer>-###`.

אותו ID חייב להופיע ב-branch, commits, reports ו-evidence.

## מחזור חיים של תוכנית

### 1. Discovery
- קריאת הקוד והחוזים.
- רישום assumptions/open questions.
- אין שינוי קוד.

### 2. Plan
- מטרה אחת ברורה.
- scope ו-non-goals.
- ownership מדויק.
- acceptance criteria.
- test plan.
- rollback.

### 3. Approval
- המתזמר בודק תלות וחפיפה.
- תוכניות מסוכנות מקבלות אישור אדם.

### 4. Execution
- סוכן עובד רק בתחום הבעלות.
- עדכונים מבוססי artifact, לא narration.

### 5. Review
שני reviews נפרדים:
1. התאמה ל-spec.
2. איכות קוד, אבטחה ותחזוקה.

### 6. Verification
- tests טריים.
- failure cases.
- artifact inspection.
- evidence נשמר.

### 7. Merge/Handoff
- orchestrator בלבד ממזג.
- producer מוסר חוזה יציב ל-consumer.
- `PROJECT-STATE.yaml` ו-`PROGRESS.md` מתעדכנים באותו merge.

## תפקידים

### Lead/Orchestrator
- מנהל סדר עבודה, state ו-budget.
- מקצה ownership.
- מונע agents מקבילים על אותם קבצים.
- היחיד שממזג.

### Research Agent
- קריאה בלבד.
- מספק מקורות והפניות מדויקות.
- אינו משנה קוד.

### Architect Agent
- contracts, boundaries ו-ADRs.
- אינו משכתב implementation ללא תוכנית.

### Developer Agent
- TDD ו-scope מוגבל.
- מספק commit ו-test evidence.

### Tester Agent
- בודק happy path ו-failure paths.
- אינו מחליש assertions כדי לקבל ירוק.

### Reviewer Agent
- review בלתי תלוי.
- מסווג findings לפי severity.

### Operations Agent
- jobs, logs, server lifecycle ועלויות.
- חייב להבטיח shutdown של GPU.

## פורמט חסם
כל BLOCKED חייב לכלול:
- מה בדיוק נכשל.
- command/input.
- expected מול actual.
- root cause ידוע או unknown.
- מה נוסה.
- owner לפתרון.
- האם downstream יכול להמשיך.
- אפשרויות והמלצה.
- תנאי סגירה.

חסם ללא owner או next action אינו תקין.

## Definition of Done
עבודה אינה DONE אלא אם:
- acceptance criteria עברו.
- tests טריים עברו.
- failure path נבדק.
- review עצמאי עבר.
- docs/contracts עודכנו.
- evidence קיים וניתן לפתיחה.
- אין שינוי לא מוסבר.
- handoff נכתב.
- merge בוצע.
- state עודכן.

## כללי עבודה לעשרות סבבים
1. סבב אחד = מטרה אחת ניתנת לאימות.
2. אין יותר מתוכנית DB/schema אחת במקביל.
3. מקביליות רק כאשר ownership והתלויות נפרדים.
4. כל סבב מתחיל בקריאת state ומסתיים בעדכון state.
5. אין לפתוח סבב חדש כאשר review קריטי פתוח.
6. context של סוכן נכתב ב-brief; אין להסתמך על זיכרון צ'אט.
7. failure נשמר כ-test או regression fixture.
8. כל 5 סבבים מבצעים architecture drift review.
9. כל 10 סבבים מבצעים roadmap/cost/risk review.
10. experimental branches נמחקים רק לאחר תיעוד תוצאה.

## מחזור אוטומציה מחייב ל־WP0–WP6

כל WP מפורק ל־`PREFLIGHT → PLAN-CHECK → IMPLEMENT → TEST → REVIEW → REWORK → VERIFY → CHECKPOINT → HANDOFF → GATE`. review ראשון read-only ו-rework הוא task חדש. Auto-recovery מוגבל לשלושה ניסיונות טכניים. observer מדווח מיד וב-heartbeat של 15 דקות בזמן פעילות, אך נשאר read-only.

## אבחון כישלונות — איסור לולאת ניסיונות (retry loop)

auto-recovery הוא רשות, לא תירוץ לירות מחדש בלי מחשבה. חובה על כל סוכן:

1. **קרא את ההודעה המלאה.** הבן *למה* הכשל, לא רק *מה* נכשל. אל תנחש.
2. **הרץ מקומית את הבדיקה הספציפית** שנכשלה לפני dispatch מחדש — משוב מהיר במקום לגלות שוב ב־CI.
3. **כל retry חייב השערה חדשה.** אין לחזור על אותה פעולה. לפני retry: root cause משוער, מה משתנה, למה שונה מהניסיון הקודם.
4. **גבול:** auto-recovery מוגבל ל־3 ניסיונות טכניים, אבל אחרי 2 כשלים רצופים באותו gate — עצור, אבחן את root cause, ודווח ל־Moshe לפני ניסיון נוסף. אין ניסיון עיוור שלישי.
5. **תעד מה נוסה.** כשל שחוזר = root cause לא אובחן, לא "עוד ניסיון".

תקדים: ריצות 71/72/74 של WP0 נכשלו שלוש פעמים מאותו root cause (delegation עדיין על OmniRoute) — כי נוסה מחדש במקום לאבחן. gate שנכשל הוא מדידה, לא דעה.

## מניעת drift של סוכנים
- system prompt קצר + brief קנוני.
- רשימת non-goals.
- ownership paths.
- output schema.
- max tool/runtime budget.
- provider/model/effort/fallback מוגדרים מראש.
- independent review.
- אין הרשאה ל-push/deploy/delete ללא אישור.
- שינויים מחוץ ל-scope נדחים גם אם “טובים”.
