## מטרת המדיניות

לאפשר ל־OmniRoute לתכנן מראש את כל המסלול עד WP6 ולהריץ אותו ברצף, תוך:

- צמצום עצירות על שאלות צפויות.
- מעבר אוטומטי בין פעולות הפיכות ומאושרות.
- שימוש ב־Anthropic כאשר היא זמינה והמשך דרך OmniRoute כאשר אינה זמינה.
- checkpoints, tests, evidence ו-reviews בכל WP.
- עצירה רק בנקודות שהן באמת החלטות אנושיות, בלתי־הפיכות או מחוץ לתחום המאושר.

## עקרון ההפעלה

האוטומציה אינה "הרצה עיוורת". היא pipeline מבוקר:

```text
PLAN-ALL
→ VALIDATE DEPENDENCIES
→ WPn PLAN
→ IMPLEMENT
→ TEST
→ INDEPENDENT REVIEW
→ REWORK
→ VERIFY
→ CHECKPOINT/HANDOFF
→ POLICY GATE
→ WPn+1
```

OmniRoute מנהל את ה־pipeline, אך כל מעבר תלוי בראיות ובתנאי הקבלה של ה־WP.

## שלב 1 — תכנון מלא לפני ביצוע

לפני הפעלת הקמפיין, OmniRoute יכין packet קנוני אחד עבור WP0–WP6 שיכלול:

1. dependency graph מלא.
2. scope ו-non-goals לכל WP.
3. inputs, outputs ו-contracts.
4. acceptance criteria מדידים.
5. test plan ו-failure paths.
6. agent roles ו-model routing.
7. retries, timeout ו-backoff.
8. checkpoint ו-rollback לכל שלב.
9. evidence ו-handoff נדרשים.
10. סיווג כל gate לפי מטריצת האישורים במסמך זה.

התכנון הכולל נועד למנוע גילוי מאוחר של החלטות צפויות. עם זאת, כל WP יקבל brief תחום לפני ביצועו כדי למנוע drift.

## שלב 2 — ביצוע WP אחר WP

לכל WP יופעל מחזור קבוע:

1. **Preflight** — אימות parent, worktree, branch, dependencies, environment ו-scope.
2. **Plan check** — אימות שה־brief תואם ל־packet הכולל.
3. **Implementation** — שינוי תחום בלבד וב־TDD כאשר יש קוד.
4. **Verification** — tests רלוונטיים, failure paths ו-artifact inspection.
5. **Independent review** — reviewer נפרד לפי מדיניות המודלים.
6. **Rework** — תיקון findings שאושרו ובדיקות חוזרות.
7. **Checkpoint** — commit או diff מזוהה, run report ו-evidence index.
8. **Gate evaluation** — בדיקה אם מותר לעבור אוטומטית או נדרש משה.
9. **Handoff** — מסירת artifact מאומת ל־WP הבא.

אסור להתחיל WP הבא לפני שה־WP הנוכחי הגיע למצב `VERIFIED` בהתאם לתנאי הקבלה שלו.

## מטריצת אישורים

### A — מאושר מראש ואוטומטי

OmniRoute רשאי לבצע ללא בקשה נוספת:

- קריאת repository, מסמכים, state, board ו-logs.
- תכנון, פירוק משימות וכתיבת briefs.
- יצירת worktree/branch/checkpoint מקומי במסגרת הפרויקט.
- כתיבת קוד בתחום WP מאושר.
- TDD, unit/integration tests, lint, build ו-validation מקומיים.
- יצירת fixtures סינתטיים וזכויות־נקיות במסגרת החוזים.
- ביקורת read-only וביקורת cross-model/cross-provider כאשר זמינה.
- תיקון findings בתחום המאושר.
- retries לכשל טכני allowlisted, עד שלושה ניסיונות.
- fallback מ־Anthropic למודל כשיר דרך OmniRoute לפי מסמך המדיניות.
- עדכון run reports, evidence, handoffs ו-Kanban status.
- מעבר לשלב הטכני הבא בתוך אותו WP לאחר שכל הבדיקות הרלוונטיות עברו.

### B — מאושר מראש בתנאים

מותר אוטומטית רק אם התנאי המצוין מתקיים ומתועד:

| פעולה | תנאי |
|---|---|
| מעבר אוטומטי ל־WP הבא | ה־WP הקודם `VERIFIED`; אין finding קריטי/מהותי פתוח; אין שינוי scope; והמעבר אינו מפעיל route או מערכת אמיתית |
| התקנת dependency | מופיעה ב־lockfile ובתוכנית המאושרת, בסביבה מבודדת, ללא credential או שירות חיצוני; אחרת נדרש אישור |
| same-provider independent review | reviewer הוא session/agent/model נפרד, החריג מתועד ואין self-review |
| תיקון אוטומטי לאחר review | התיקון בתוך scope ואינו משנה contract, threshold או architecture |
| שחזור מכשל worker/worktree | root cause טכני allowlisted, checkpoint תקין ו-retry מוגבל |
| יצירת successor task | מוגבל לגרף WP0–WP6 ול־packet המאושר, ללא הרחבת מוצר |

### C — תמיד דורש אישור אנושי מפורש

האוטומציה חייבת לעצור ולפנות למשה לפני:

- שינוי scope, product direction, contract או architecture מהותית.
- החלשת threshold, test, security control או acceptance gate.
- מחיקה בלתי־הפיכה של נתונים או history.
- שינוי credentials, הרשאות, secrets או trust boundary.
- push/merge לענף מוגן אם לא אושר במפורש במסגרת ההפעלה.
- route activation, production deployment או חשיפה למשתמשים.
- הוצאה כספית או שימוש בשירות בתשלום שלא אושר.
- H200/GPU/cloud/remote execution או ‏G7/G8.
- implementation של PLAN-003; זהו Geometry מקומי אפשרי אך הוא מחוץ ל־packet של WP0–WP6 ודורש אישור נפרד.
- שימוש בנתוני לקוח/קלט פרטי מחוץ למחשב המקומי.
- קבלת סיכון security/rights/privacy ידוע.
- החלטה סופית של WP6 על activation; WP6 מכין decision packet בלבד.

## טיפול בזמינות מודלים

1. OmniRoute בודק זמינות לפי runtime, לא לפי הנחה.
2. Anthropic זמינה ומתאימה: המשימה מנותבת אליה.
3. Anthropic אינה זמינה: OmniRoute בוחר חלופה כשירה וממשיך.
4. fallback מתועד ואינו משנה scope או gates.
5. משימת spatial/geometry קריטית שבוצעה ללא Anthropic מסומנת לביקורת משלימה, אך עבודה הפיכה יכולה להמשיך.
6. אם אין שום מודל כשיר או אין הוכחת model identity, המשימה נחסמת טכנית.

## טיפול בכשלים

### כשלים שמקבלים auto-recovery

- timeout זמני.
- HTTP 429 או quota של ספק יחיד כאשר קיימת חלופה מאושרת.
- crash של worker לאחר checkpoint.
- transient API/network error מקומי.
- worktree/lock שניתן לשחזר באופן דטרמיניסטי.
- test flake שהוגדר מראש ונבדק מחדש במספר מוגבל של ניסיונות.

### כשלים שאסור לעקוף אוטומטית

- test אמיתי שנכשל בעקביות.
- finding קריטי או מהותי פתוח.
- זכויות או provenance לא מוכחים.
- security/privacy incident.
- contract ambiguity.
- model identity לא מוכחת כאשר הזהות היא תנאי gate.
- צורך בשינוי scope, threshold או product behavior.

### Circuit breaker

- עד שלושה retries טכניים לכל failure class.
- לאחר מכן הכרטיס עובר ל־`BLOCKED` עם root cause, evidence ו-next action.
- אין cron שמבטל חסימות אנושיות או משנה סטטוס ביצועי.

## מדיניות מעבר אוטומטי בין WP

מעבר אוטומטי מ־WPn ל־WPn+1 מותר רק אם:

- כל acceptance criteria של WPn עברו.
- tests טריים עברו.
- evidence קשור ל־checkpoint המדויק.
- אין findings קריטיים או מהותיים פתוחים.
- reviewer identity מתועדת.
- parent/child dependencies תקינות.
- scope של WPn+1 כבר כלול ב־packet המאושר.
- הפעולה הבאה אינה מסוג C.

אם תנאי אחד חסר, לא מתחילים את ה־WP הבא.

## Checkpoint, rollback ו-resume

כל WP חייב להסתיים או להיעצר עם:

```text
WP_ID:
STATUS:
CHECKPOINT_SHA_OR_DIFF:
TEST_COMMANDS_AND_RESULTS:
EVIDENCE_INDEX:
REVIEW_VERDICT:
OPEN_FINDINGS:
FALLBACKS_USED:
ROLLBACK_POINT:
NEXT_ALLOWED_ACTION:
HUMAN_ACTION_REQUIRED: yes/no
```

לאחר crash או restart, OmniRoute ממשיך רק מה־checkpoint האחרון שאומת. אין להסתמך על זיכרון צ'אט או על working tree לא מתועד.

## דיווח ומעקב

- Kanban הוא מקור האמת למצב execution.
- Git, run reports, evidence ו-handoffs הם מקור האמת לתוצרים.
- observer חיצוני נשאר read-only.
- נשלח עדכון מיד עם שינוי מהותי.
- בזמן עבודה פעילה נשלח heartbeat תמציתי כל 15 דקות.
- כל עדכון יתחיל באחד מהסיווגים:
  - `ACTION REQUIRED`
  - `INFORMATION ONLY`
  - `TECHNICAL BLOCKER — AGENT HANDLING`

## גבולות WP0–WP6

- האוטומציה מוגבלת לחלק 1 המקומי.
- WP0–WP5 יכולים להתקדם לפי המדיניות כאשר התנאים עברו.
- WP6 רשאי לבצע audit ולהכין decision packet.
- WP6 אינו רשאי להפעיל routes; activation דורש אישור משה שמציין scope, versions ו-rollback owner.
- אין מעבר אוטומטי ל־PLAN-003. PLAN-003 אינו H200: הוא Geometry מקומי אפשרי, אך דורש packet/PLAN ואישור נפרדים.
